# 연구: 도메인 → 기능 → 실행 길

Status: Accepted  
Scale: Large  
Date: 2026-08-15

인터뷰로 잠근 제품 결정을 코드 사실과 바깥 사례에 맞춰 기록한다.  
구현은 이 문서가 아니라 `docs/plans/hierarchy-map.md`를 따른다.

## Problem

지금 엔진은 파일을 읽고, 함수를 찾고, 큰 카드를 만든다.  
사용자가 원하는 것은 **일 덩어리 → 그 안의 동작 → 그 동작이 코드에서 어떻게 도는지**다.

이 세 층이 코드에서 한 줄로 이어지지 않으면, 지도는 파일 그림이 되거나 코드와 다른 이야기가 된다.

## Finished Target

화면+서버가 있는 웹앱 하나에서:

1. 첫 화면에 일 덩어리(비즈니스 도메인)가 바로 보인다.
2. 덩어리를 누르면 그 안의 동작(단위 기능)이 펼쳐진다. 너무 많으면 화면에서만 묶는다.
3. 동작을 누르면 **코드에서 실제로 찾은 일만**, 그 기능의 순서로 보인다.
4. 확신이 없으면 숨기지 않고 “확실하지 않음”을 붙인다.
5. 없는 일을 지어내서 그리지 않는다.
6. AI는 이름을 읽기 쉽게 바꿀 수 있으나, 덩어리·동작·길을 **만들지 않는다**.

사용자는 이 정보로 스스로 가치를 만든다. 도구는 줄 단위로 읽는 비용을 줄인다.

## Current Architecture Facts

- 정적 파이프라인: 스캔 → 언어 분석 → 참조 → 프레임워크 보강 → 그래프 → 함수별 실행 그래프 → 도메인 묶기 → Overview.
- 기능은 바깥 동작(HTTP 등) 기준으로 만들고, 도메인 배정은 묶음의 **대표 이름**과 같을 때만 붙는다. 그래서 동작이 카드 밖으로 떨어질 수 있다.
- 실행 그래프는 **모든 함수**마다 만든다. “이 기능의 일 순서”가 아니다.
- 앱은 큰 카드와 오른쪽 칸이 있다. 동작은 최대 8개만 보이고, 실행 길은 숫자만 있다.
- AI는 별도 단계다. 프롬프트는 도메인 이름만 다루고 기능·길을 만들지 말라고 한다.
- 앱은 AI 도메인이 비면 정적 결과까지 버린다.

## Comparable Landscape

대부분 코드 지도는 **폴더·파일·import**를 그린다.

- [CodeMap](https://github.com/omertt27/CodeMap): 로컬에서 파일·의존 그래프. 파서 사실만, LLM으로 구조를 안 만듦.
- [reality-map](https://github.com/g0GobliN/reality-map): 모듈을 더블클릭해 파일·심볼로 들어감. 계층은 폴더에 가깝다.
- [DevLens](https://devlens.io/): 파일·컴포넌트·의존 + AI 요약. “바꾸면 뭐가 깨지나”가 강점.
- [C4 model](https://c4model.com/): 사람 지도는 맥락 → 컨테이너 → 컴포넌트 → 코드로 **점점 자세히**. 한 화면에 코드를 다 안 올린다.

시사점:

- 바깥 도구의 기본 층은 **파일**이다. VisualMap의 기본 층은 **일 덩어리와 동작**이어야 차별이 된다.
- 자세히 보기는 눌러서 들어간다. 첫 화면에 코드를 다 올리지 않는다. (인터뷰 3A와 같음)
- 구조를 AI가 지어내면 신뢰를 잃는다. 이름은 AI, 뼈대는 코드.

## Decision: 지도의 세 층

Context:
- 사용자는 할 일 앱으로 설명했다. 일정 관리 → 일정 등록/삭제 → 등록이 코드에서 도는 순서.
- 4층(대분류)을 고민했으나, 일정 관리가 이미 묶음이다.

Options:
- A: 분석도 4층 — 중복 묶음, 엔진·화면이 커짐
- B: 항상 3층만 — 동작이 30개면 목록이 김
- C: 분석은 3층. 동작이 많을 때만 **화면에서** 묶음

Decision:
- C

Consequences:
- 엔진은 도메인 / 기능 / 길을 만든다.
- “대분류”는 데이터 모델에 넣지 않는다. 화면 정렬 힌트만 나중에 가능하다.

## Decision: 길에 올리는 것

Context:
- 사용자는 한 줄 코드 재생을 원하지 않는다.
- 층(화면/서버/DB)만 그리면 모든 기능이 비슷해 보인다.
- **코드에 없는 것은 보여 주지 않는다.**

Options:
- A: 코드에서 찾은 일만, 읽기 쉬운 이름
- B: 이해용으로 없는 단계도 창작
- C: 창작하되 “추측” 표시

Decision:
- A. 확신이 낮으면 그 사실을 **빼지 않고** “확실하지 않음”만 붙인다. 없는 일을 추가하지는 않는다.

Consequences:
- 사용자 보이는 길은 “이 기능의 진입점에서 실제로 이어진 코드 일”이다.
- 지금처럼 프로젝트의 모든 함수 CFG를 길이라고 보여 주면 안 된다.
- 함수 그래프는 내부 재료로 남기고, 화면에 올리는 길은 기능 범위로 자른다.

## Decision: 1.0 범위

Context:
- 언어 10개 배선은 있다. 깊은 추출은 일부만.
- 세 층 연결이 안 된 채 언어를 늘리면 넓게 틀린 지도가 된다.

Options:
- A: 화면+서버 웹앱 한 종류에서 세 층이 맞으면 1.0
- B: 여러 언어에서 카드만 나오면 1.0
- C: 10언어가 같은 깊이여야 1.0

Decision:
- A

Consequences:
- 기준 저장소는 화면과 서버가 있는 웹앱 하나.
- 다른 언어는 같은 세 층이 깨지지 않는지 **회귀**만. 동시 깊게 만들지 않음.

## Decision: 정보의 양

Context:
- 원칙: 최대한의 정보를 바로 이해되게. 가치는 사용자가 창출.
- 첫 화면에 다 올리면 줄 단위 코드의 다른 버전이 된다.

Decision:
- 첫 화면은 큰 덩어리. 정보는 눌러서 꺼낸다.
- 캔버스 vs 옆 패널은 화면 작업 때 정한다. 제품 층과 무관.

## Decision: AI

Decision:
- AI는 이름(읽기)만. 덩어리·동작·길의 존재는 정적 결과가 정한다.
- AI가 없어도 지도는 보여야 한다.
- 확신이 낮으면 표시. 숨기거나 예쁘게 채우지 않음.

## Architecture Fit

기존 파이프라인을 교체하지 않는다.  
끊긴 연결만 고치고, “길”의 **보이는 의미**를 기능 범위로 바꾼다.

```text
코드 사실(함수, 호출, 바깥 동작)
  → 동작(기능) = 바깥에서 들어오는 일 하나
  → 덩어리(도메인) = 관련 동작의 묶음
  → 길 = 그 동작의 진입점에서 실제로 이어진 일 순서
  → 화면 = 덩어리 먼저, 누르면 동작, 누르면 길
  → 이름 = 선택적 AI
```

## Integration Boundaries

- 엔진: 도메인·기능·길의 연결이 맞아야 한다. 화면보다 먼저.
- 앱: 펼치기. 기능 8개 절단 제거. AI 없어도 표시.
- 설정·언어 추가: 1.0 이후.

## Data / Privacy

- 분석은 로컬. 이 계획으로 원격 업로드를 추가하지 않는다.
- AI CLI는 기존처럼 사용자가 켠 경우에만. 지도 뼈대는 AI 없이 성립.

## Rollout / Rollback

- 단계마다 엔진 동작이 이전보다 **연결이 맞는지**로 판정.
- 단계 실패 시 그 단계 diff만 되돌린다. 파이프라인 전체 교체 없음.

## Test / Verification

- 작은 할 일 앱 형태(등록/삭제/로그인) fixture로 세 층을 검사.
- 기준 웹앱 하나에서 사람 확인: 빠진 동작, 한 카드에 다른 일, 길에 없는 일.
- 언어 10개 동등 깊이는 1.0 성공 조건이 아님.

## Operational Risk

- 모든 함수 그래프를 화면에 올리면 크고 느리다. 보이는 길은 기능 범위로 제한.
- 큰 JSON 한 파일은 앱이 이미 안 쓴다. 이 계획도 그걸 다시 필수화하지 않음.
