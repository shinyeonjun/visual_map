# 동적 프로젝트·다언어 실행 흐름 분석 연구

- 상태: 제안
- 규모: Large
- 작성일: 2026-08-01
- 목적: 프로젝트를 열 때마다 언어·프레임워크·진입점을 동적으로 분석하면서도, 확인되지 않은 관계를 확정된 실행 흐름처럼 보여주지 않는 제품 경계를 결정한다.

## 1. 문제 정의

사용자가 원하는 결과는 단순한 파일 목록이나 `route` 목록이 아니다. 다음과 같은 질문에 답하는 실행 흐름이다.

```text
API/이벤트 진입점
  -> 미들웨어·검증·인증
  -> 실제 핸들러
  -> 서비스/도메인 호출
  -> 저장소·쿼리
  -> 테이블·컬럼 또는 외부 서비스·이벤트
  -> 성공/실패 경로
```

문제는 언어와 프레임워크마다 이 흐름을 선언하는 방법이 다르고, 같은 이름이 여러 파일에 존재하거나 동적 디스패치·DI·리플렉션·코드 생성이 개입한다는 점이다. 따라서 “모든 파일을 읽었으니 모든 관계를 안다”는 정책은 살충제 패러독스를 만들고, 특정 샘플 프로젝트에 맞춘 규칙은 다른 프로젝트에서 중복·오탐·누락으로 무너진다.

## 2. 현재 저장소에서 이미 확보된 경계

현재 계약과 구현에는 다음 장치가 이미 있다.

1. 공식 언어 범위는 TypeScript, JavaScript, Python, Java, Kotlin, C#, C, C++, Go, Rust, Swift, PHP, Ruby, Dart의 14개로 선언되어 있다.
2. 프레임워크·ORM 지원 목록은 언어별로 선언되어 있다. 선언되지 않은 조합은 이름만으로 정밀 지원을 주장하지 않는다.
3. 코드 분석과 DB 분석의 책임이 분리되어 있다. 코드 엔진은 `Query`/`DbReference` 증거를 만들고, 확정된 코드-DB 관계는 통합 스냅샷에서만 만든다.
4. 관계에는 `confirmed`, `structural`, `candidate`, `unknown` 상태가 있고, 분석 결과에는 `complete`, `partial`, `failed`, `stale`, `unsupported` 상태가 있다.
5. HTTP만이 아니라 RPC, 이벤트 소비자, 큐 핸들러, 스케줄 작업, CLI, 웹훅을 진입점으로 표현할 수 있는 공통 모델이 있다.
6. UI는 이미 인벤토리·맵·답변·영향 범위를 공통 투영으로 처리하므로 언어별 화면을 따로 만드는 방향은 기존 구조와 맞지 않는다.

이 사실들은 새 기능의 출발점이지 교체 대상이 아니다. 특히 `unknown`을 빈 값으로 숨기거나 이름만 보고 `confirmed`로 승격하면 현재 계약을 위반한다.

## 3. 선택지 비교

| 선택지 | 방식 | 장점 | 근본 위험 | 판정 |
| --- | --- | --- | --- | --- |
| A. 완전 고정 | 언어·폴더·프레임워크·흐름을 제품 코드에 고정 | 초기 결과가 예측 가능하고 구현이 단순함 | 새 프로젝트 구조, 버전, 비표준 패턴마다 코드 수정 필요. 특정 샘플에 과적합 | 기각 |
| B. 완전 동적 | 모든 언어·프레임워크를 파일·이름·AST 휴리스틱으로 자동 추론 | 새 프로젝트를 즉시 읽을 수 있음 | 오탐 관계를 확정 관계로 표시하기 쉽고, 동적 언어·DI·ORM에서 신뢰도를 보장할 수 없음 | 기각 |
| C. 하이브리드 | 프로젝트 구조·파일·언어·후보 진입점은 동적 탐색. 의미 있는 확정 관계는 선언된 provider/framework pack과 증거 규칙으로만 생성 | 범용성과 신뢰성을 동시에 확보. 미지원 프로젝트도 구조적으로 볼 수 있고, 지원 프로젝트만 정밀 흐름을 약속 | 지원 팩과 검증 fixture를 계속 관리해야 함. UI에 상태·갭을 명확히 노출해야 함 | **채택** |

## 4. 채택 정책

### 4.1 프로젝트마다 동적으로 해야 하는 것

- 실제 파일과 모듈, 언어 혼합 상태, 매니페스트, 생성 산출물 제외 범위
- provider가 읽을 수 있는 심볼·정의·참조·직접 호출·파일 위치
- 프레임워크 팩이 발견한 진입점, 핸들러, 미들웨어, 컨트롤러, 저장소 후보
- 분석 실행의 스냅샷·부분 성공·실패·stale 상태와 관계 갭
- 사용자가 선택한 진입점에서 bounded hop으로 계산한 현재 화면의 실행 흐름

프로젝트 이름, 특정 폴더명, `controllers/` 같은 관례를 제품 전체의 필수 조건으로 만들지 않는다. 이름은 후보 생성에만 사용하고 확정 근거가 될 수 없다.

### 4.2 제품이 고정해서 보장해야 하는 것

- 공식 지원 언어 14개와 각 언어의 지원 프레임워크·ORM·DB 범위
- 모든 provider의 공통 결과 스키마와 안정적인 ID·파일 위치·라인 증거
- 관계의 진실성 상태와 승격 규칙
- 미지원 언어·프레임워크를 “미지원” 또는 “구조적 분석만 가능”으로 표시하는 정책
- 코드-DB 관계를 database-memory의 정확한 스냅샷 확인 뒤에만 확정하는 정책
- 성능 상한, hop 상한, 파일·노드·관계 수 상한, 취소·타임아웃, 캐시 무효화

즉, “무엇을 읽을지”는 프로젝트마다 동적이고 “무엇을 확정이라고 말할지”는 제품 계약으로 고정한다.

## 5. 지원 등급

| 등급 | 제공 범위 | 허용되는 UI 표현 |
| --- | --- | --- |
| T0 읽기 가능 | 파일·언어·모듈·기본 심볼 인벤토리 | 구조/탐색 결과. 실행 흐름 확정 아님 |
| T1 공통 코드 지능 | 정의·참조·직접 호출·소스 위치·일부 진입점 | 증거가 있는 코드 관계와 후보/갭 |
| T2 팩 검증 정밀 분석 | 선언된 언어/provider/framework pack의 route/handler/middleware/DI/ORM 규칙 | 검증된 실행 흐름. 모든 hop에 증거 필요 |
| T3 통합 확정 | T2 결과와 database-memory의 정확한 스냅샷 조인 | 확정된 READS/WRITES와 테이블·컬럼 영향 |

지원 등급은 프로젝트 전체의 단일 플래그가 아니라 언어·프레임워크·분석 항목별 capability로 기록한다. 예를 들어 Java는 T2지만 Kotlin 일부 모듈은 T1일 수 있고, route는 T2여도 ORM은 T1일 수 있다.

## 6. 책임 분리

### 공통 어댑터/프레임워크가 담당할 것

- 안정적인 엔티티·관계 ID 정규화
- 스냅샷과 분석 실행의 상태 관리
- `confirmed/candidate/unknown/gap` 및 품질 사유의 공통 표현
- 파일·라인·소스 조각·provider 출처의 증거 모델
- 진입점에서 bounded path를 찾는 공통 traversal
- 중복 제거, 관계 충돌, 모호성 처리, 실패 격리
- UI용 인벤토리·맵·답변·영향 범위 투영

### 언어/provider 어댑터가 담당할 것

- 언어별 AST/LSP/provider 결과를 공통 심볼·호출·위치로 변환
- 언어의 import, overload, receiver, module, async/generator 의미
- 정적 분석으로 안전하게 확인 가능한 직접 호출과 모호성

### framework/ORM pack이 담당할 것

- route/controller/handler/middleware/DI/consumer/scheduler의 문법과 관례
- framework별 handler ownership과 중복 제거
- ORM/query builder/raw SQL의 증거 추출
- 선언된 fixture와 negative/ambiguity fixture를 통한 품질 기준

언어별 화면, 프로젝트별 특례, 이름만으로 관계를 확정하는 공통 휴리스틱은 만들지 않는다.

## 7. 목표 흐름과 실패 처리

정상적인 확정 흐름은 다음과 같다.

```text
EntryPoint
  -HANDLES-> Handler
  -CALLS-> Service
  -CALLS-> Repository/Operation
  -EXECUTES_QUERY-> DbReference
  -READS/WRITES-> Table/Column   (database-memory 정확 매칭 후)
```

다음 경우에는 관계를 숨겨서 성공처럼 보이지 않고, 갭으로 남긴다.

- 같은 이름의 함수가 여러 개라 대상이 모호함
- 문자열·주석·파일명만으로 route 또는 handler를 추정함
- DI·reflection·코드 생성 대상의 실제 구현을 정적으로 확인하지 못함
- ORM 쿼리의 테이블/컬럼을 정확한 DB 스냅샷과 연결하지 못함
- provider가 부분 실패했거나 현재 소스와 스냅샷이 stale 상태임

UI에서는 확정 경로와 후보/미확인 경로를 같은 선으로 섞지 않는다. 사용자가 “왜 여기서 끊겼는지”를 파일·라인·사유로 확인할 수 있어야 한다.

## 8. 살충제 패러독스 방지 기준

한 프로젝트의 기대 출력만 고정하는 회귀 테스트는 충분하지 않다. 각 팩에는 다음 변형을 최소 세트로 둔다.

- 이름 변경: handler/service 이름과 파일명을 바꿔도 의미 관계가 유지되는지
- 파일 이동: 폴더 깊이와 모듈 경계를 바꿔도 ID·호출이 맞는지
- 순서 변경: 선언 순서와 import 순서를 바꿔도 결과가 같은지
- 동명이인: 같은 이름의 정의를 추가했을 때 확정 대신 ambiguity/gap인지
- 미지원 변형: 유사한 이름의 다른 framework를 잘못 확정하지 않는지
- 부분 실패: 한 provider/파일이 실패해도 전체 결과가 거짓 확정으로 바뀌지 않는지
- 재실행/캐시: 동일 스냅샷의 결과가 안정적이고 소스 변경 시 stale 결과가 재사용되지 않는지

통합 검증은 Petclinic과 node-express-boilerplate에만 맞추지 않고, 언어별 최소 fixture, cross-file fixture, negative fixture, metamorphic fixture, 실제 공개 저장소 샘플을 분리한다.

## 9. 남은 제품 결정

현재 권고안은 “공식 지원 범위는 14개 언어와 선언된 팩으로 유지하고, 범위를 벗어난 프로젝트는 T0/T1 구조·호출 분석만 제공하며 확정 실행 흐름을 주장하지 않는다”이다.

이 정책을 승인하면 다음 구현 순서는 capability 계약 → 공통 flow traversal → 언어/provider 품질 매트릭스 → framework/ORM/DB 통합 → UI 갭·증거 표시 → 대규모 실프로젝트 검증이다. 승인 전에는 언어별 UI 분기나 무제한 휴리스틱을 추가하지 않는다.
